## 4. 启动 Rerank 服务（TEI）

### 4.1 为什么这一步是**必须**的，不是可选优化

Dify 官方文档在「向量检索 / 全文检索 / 混合检索」三处均明确写明：

> **TopK 和 Score 设置仅在 Rerank 阶段生效。因此，要应用这些设置中的任何一项，需要添加并启用 Rerank 模型。**

翻译成实际后果：

- 不配 Rerank → Dify 界面**照样让你填** Score 阈值和 TopK，但**两个值一个都不生效**
- 而需求文档 FR-03 的整条调参链路（阈值 0.5 / TopK 8 / 知识库级+节点级两级检索）全部建立在这两个值上
- 也就是说：**不配 Rerank，FR-03 和 FR-09（评测集调参）会静默失效**——界面显示正常，报告数据全是噪声

且 **Ollama 不提供 Rerank 接口**（只有 completion / embedding 两种 capability），无法用现成模型顶替。

### 4.2 镜像版本选择（踩坑记录）

TEI 在 GHCR 的标签约定是 `{架构}-{版本}`，**没有** `-cuda-12.4` 这种写法：

```powershell
# ❌ 错误写法，tag 不存在
ghcr.io/huggingface/text-embeddings-inference:1.8.2-cuda-12.4
# ERROR: failed to resolve reference ... not found
```

可用架构前缀：`cpu` / `turing` / `86` / `89` / `hopper`。

**本机选 `turing-1.2`**——2080 Ti 是 Turing 架构（sm_75），HF 官方为它单独出了构建版本，不要用 `latest`（默认按 Ampere 及以上优化）。

### 4.3 启动命令

```powershell
docker run -d --name tei-rerank --gpus all --restart unless-stopped `
  --network docker_default `
  -p 9999:80 `
  -e HF_ENDPOINT=https://hf-mirror.com `
  --shm-size 1g `
  ghcr.io/huggingface/text-embeddings-inference:turing-1.2 `
  --model-id BAAI/bge-reranker-v2-m3 `
  --dtype float16 `
  --max-client-batch-size 32 `
  --max-batch-tokens 8192
```

各参数说明：

| 参数 | 作用 |
| --- | --- |
| `--network docker_default` | **关键**：直接接入 Dify 的网络，Dify 侧填 `http://tei-rerank:80` 即可，不必走 `host.docker.internal` |
| `-p 9999:80` | 宿主机映射，便于手工 curl 验证 |
| `-e HF_ENDPOINT=https://hf-mirror.com` | 国内下载加速（首次拉权重约 2.3GB） |
| `--dtype float16` | 2080 Ti 有 FP16 张量核心；权重降到约 1.1GB |
| `--shm-size 1g` | 避免大批量分词时共享内存不足 |

首次启动会下载权重，约 4~5 分钟，日志里出现 `Ready` 才算就绪。

### 4.4 验证

```powershell
# 1) 容器状态 + 关键日志
docker ps --filter "name=tei-rerank" --format "{{.Names}}  {{.Status}}  {{.Ports}}"
docker logs tei-rerank 2>&1 | Select-Object -Last 5
# 期望看到：Starting Bert model on Cuda(...) ... Starting HTTP server: 0.0.0.0:80 ... Ready

# 2) 健康检查
Invoke-WebRequest -Uri "http://127.0.0.1:9999/health" -TimeoutSec 10
```

### 4.5 实测打分样例（可直接作为评测集基线）

查询：`住院医疗险的等待期是多久`

| 片段 | score |
| --- | --- |
| 除另有约定外，自本合同生效之日起 **30 日**内（含第 30 日）为等待期 | **0.7368** |
| 犹豫期为 **15 日**，自收到保险合同之日起计算 | 0.6700 |
| **90 日**内本公司承担的责任有所不同，请注意 | **0.0596** |

**这张表有两个用途：**

1. 验证服务确实在工作（分数有区分度，不是常数）
2. **暴露一个真实的调参风险**：需求文档 FR-09 种子里的第 ④ 条（两款产品等待期不同，作跨产品对比题），重疾险那条「90 日内责任有所不同」在纯语义下**只有 0.0596**。按默认阈值 0.5，它会被直接滤掉 ⇒ 跨产品对比题会漏召回。

   这不是 bug，而是**混合检索（关键词权重）要解决的典型场景**：「90日责任有所不同」与「等待期」没有词面重叠，纯向量召不回。配混合检索时把关键词权重调高（如语义 0.7 / 关键词 0.3）能否救回来，是 FR-09 评测集应当实测的第一组调参数据。

## 6. 在 Dify 中填什么（速查表）

三个模型供应商都装在 Dify 的「设置 → 模型供应商」里，**Rerank 那个必须先装**，否则知识库里选不到重排模型。

| 供应商类型 | Base URL / 地址 | 模型 | 模型类型 |
| --- | --- | --- | --- |
| **Ollama**（第 1 个） | `http://host.docker.internal:11434` | `qwen3.5:9b` | LLM |
| **Ollama**（第 2 个） | `http://host.docker.internal:11434` | `bge-m3:latest` | Text Embedding |
| **TEI** | `http://tei-rerank:80` | `BAAI/bge-reranker-v2-m3` | Rerank |

> ⚠️ Ollama 的地址必须写 `host.docker.internal:11434`，**不能写 `127.0.0.1`**——Dify 跑在容器里，容器的 127.0.0.1 是容器自己，不是宿主机。这是本地部署最常见的连不上原因。

## 7. 显存预算与串行约束

本机只有**一张** 2080 Ti（22528 MiB），且已被 ComfyUI 模型栈占用过。

| 状态 | 实测 used |
| --- | --- |
| 空闲基线 | ~1028 MiB |
| + TEI reranker | 2542 MiB（TEI 约占 1.5 GB） |
| + `qwen3.5:9b` 推理 | 另需约 7 GB（预估，未实测） |

**约束：**

1. **27B / 30B 模型不要和另两个模型同时驻留**——17~18 GB 本身就接近占满 22 GB 卡的 80%，叠任何一个都会 OOM。本项目用 `qwen3.5:9b`。
2. **跑本项目前先卸载 ComfyUI 权重**。ComfyUI 跑完**不自动卸载**，实测出图后显存会从 8484 MiB 涨到 13659 MiB（残留约 5.2 GB）。若 RAG 链路因此 OOM 或首 token 变慢，先清显存：

   ```powershell
   curl.exe -s -X POST http://127.0.0.1:8000/free `
     -H "Content-Type: application/json" `
     -d '{"unload_models":true,"free_memory":true}'
   ```

   清完回到约 1.5 GB 基线再启动。
3. 验收判据看 `nvidia-smi` 的显存指纹，**不要只看进程退出码**——显存不足时可能不报错直接静默失败。

## 8. 忘记密码的恢复

Dify 自托管默认**没有配 SMTP**（`.env` 里没有任何 `MAIL_*` 配置），所以登录页的「忘记密码」收不到邮件。

恢复脚本：`scripts/reset_dify_password.py`

```powershell
& "C:\Python312\python.exe" "D:\project\private\new_life\local\RAG_demo\scripts\reset_dify_password.py"
```

**脚本必须在你自己开的 PowerShell 窗口里运行**——密码通过 `getpass` 本地输入，不经过任何第三方。

### 实现要点

Dify 1.17 的密码哈希在 `api/libs/password.py`：

```python
salt = secrets.token_bytes(16)
dk   = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt, 10000)
hash = base64.b64encode(binascii.hexlify(dk))   # 注意是 base64(hex)，不是 base64(原始字节)
salt = base64.b64encode(salt)
```

⚠️ 这个「先 hexlify 再 base64」的双重编码很容易写错，写错了会显示重置成功但**永远登不进去**。脚本已用固定 salt + 假密码做过逐字节对照验证：

```
Dify 容器输出：e68a5c697f2a4dab2610c13e055c17da4e42a3306770eae4d95be89cadccc1f1
脚本输出    ：e68a5c697f2a4dab2610c13e055c17da4e42a3306770eae4d95be89cadccc1f1
```

### 密码规则

由 Dify 自身的 `valid_password()` 强制校验：**≥ 8 位，且必须同时包含字母和数字**。`jossion`、`12345678` 都会被拒绝。

## 10. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `failed to resolve reference ... text-embeddings-inference:1.8.2-cuda-12.4: not found` | TEI 标签无 `-cuda-12.4` 写法 | 用 `{架构}-{版本}`，本机为 `turing-1.2` |
| TEI 日志卡在 `Starting download` 很久 | 直连 HF 慢 | 已配 `HF_ENDPOINT=https://hf-mirror.com`；仍失败则 `docker rm -f tei-rerank` 后加该变量重建 |
| Dify 里 Ollama 供应商测试失败 | 填了 `127.0.0.1` | 改成 `host.docker.internal:11434` |
| Dify 里 TEI 供应商测试失败 | 未在同一网络 | 确认 `docker inspect tei-rerank` 的网络含 `docker_default`，地址填 `http://tei-rerank:80` |
| 知识库里没有 Rerank 模型可选项 | TEI 供应商未安装或未填模型类型 | 「设置 → 模型供应商」中该供应商的模型类型须选 **Rerank** |
| 重置密码后仍登不进去 | 哈希编码写错（少了 hexlify 一层） | 见 §8 对照验证 |
| OOM / 首 token 明显变慢 | ComfyUI 权重未卸载 | 见 §7 第 2 条 |
| 重启后 Rerank 没了 | 未设自动重启 | 启动命令已带 `--restart unless-stopped`，确认未被手工 `docker rm` |
