## 1. 一句话结论

**参数能救回「该答却拒答」，救不了「答的是别的产品的条款」。** 把检索阈值从 0.3 降到 0.1，
误拒率从 26% 降到 5%、引用命中率从 50% 升到 65%；但 42 条应答题里仍有 4 条串档、
3 条同名章节错配——这部分**不是参数问题，是「三份条款塞在一个知识库、检索前没有产品约束」
的架构问题**，本轮已定位清楚，留作下一阶段。

## 3. 最重要的发现：阈值改在了不生效的那一层

r002 把 `datasets.retrieval_model.score_threshold` 从 0.3 改成 0.1，跑完整 52 条：

| 指标 | r001（0.3） | r002（知识库级改 0.1） |
| --- | --- | --- |
| 平均引用条数 | 2.87 | **2.87** |
| 首条分数均值 | 0.7302 | **0.7302** |
| 引用条数发生变化的用例 | — | **0 条 / 52** |

**一字不差。** 检索节点自己还带着 `multiple_retrieval_config.score_threshold: 0.3`，运行时吃的是它。
改掉节点级之后，5 条原本 0 引用的用例立刻全部召回内容（分数 0.1076 ~ 0.2666）。

> 脚本层面的坑：`score_threshold` 在知识库级和节点级**同名**，按 `if key in dataset: ... continue`
> 的顺序匹配会永远只改到知识库级、永远碰不到节点级——这就是「改了没反应」最常见的来源。
> 本项目 `scripts/dify_params.py` 已改为用 `node.` 前缀显式区分作用域。

## 4. 参数扫描（只检索不调 LLM，秒级）

用 Dify `/v1/datasets/{id}/retrieve` 扫参数，**不进 LLM**，一组 8 秒、全量 52 条。
全量评测一轮要 15 分钟，扫参数要几十组——先扫后验是唯一可行的调参姿势。

### 4.1 score_threshold

| 阈值 | 章节命中 | 产品正确 | 目录噪声 | 平均条数 |
| --- | --- | --- | --- | --- |
| 0.40 | 44% | 60% | 13 | 2.1 |
| **0.30（原配置）** | **59%** | **67%** | 13 | 2.9 |
| 0.20 | 65% | 81% | 16 | 3.8 |
| 0.15 | 74% | 86% | 18 | 5.0 |
| **0.10（采用）** | **79%** | **88%** | 18 | 6.5 |
| 0.05 | 85% | 88% | 19 | 8.3 |
| 0.00 | 94% | 88% | 21 | 18.6 |

**单看这张表会得出「越低越好」的结论，端到端跑出来却不是。** 见 §5。

### 4.2 top_k 与权重

| 配置 | 章节命中 | 备注 |
| --- | --- | --- |
| top_k=5 | 53% | 明显不够 |
| top_k=10 | 71% | |
| top_k=15 / 20 | 76% | 进入平台期 |
| **top_k=30（现值）** | **79%** | 平台期末尾，再大无收益 |
| vector/keyword 权重 0.1 ~ 0.9 | **全部 79%** | 旋钮在当前工作点**完全不起作用** |

权重无效有两种可能：「被 rerank 压制」或「旋钮没接上」。为区分，额外在**关闭 rerank** 的前提下
对照了一遍——结果仍是 79%/32 条完全一致，说明**不是没接上，而是在当前工作点上对候选集没有影响**
（阈值 0.1 + top_k 30 时候选集本来就基本等于整个池子，调权重只改排序不改入选）。
**结论：这两个旋钮在本项目上不值得再花时间。**

### 4.3 ⚠️ top_k ≥ 33 会静默返回空集

| top_k | 结果 |
| --- | --- |
| 30 / 31 / 32 | 正常（1 条） |
| **33 及以上** | **HTTP 200、0 条记录、零异常** |

在 Dify 界面把 top_k 设成 33 以上，问答会**静默失效**——不报错、不告警，只是什么都答不出来。
调参时如果撞到这个边界，很容易误判成「知识库坏了」。

## 5. 为什么「召回率最高」不等于「答得最好」

阈值 0.1 在检索层命中 79%（比 0.3 的 59% 高 20 个百分点），端到端通过数却没涨。
把 r003 相对基线的 8 条回归逐条看了答案，原因有两个：

### 5.1 上下文稀释 + 目录页污染（6 条）

引用条数从 2.9 涨到 6.5，多出来的低分片段里混着**「阅读指引」「条款目录」页**。
模型读到目录页里写着 `2.3 保险责任`，就断定「文中没有写具体天数」，然后**用行业常识补**：

> 「在中国大陆地区的商业保险监管规定及行业惯例中，长期重疾险的犹豫期标准时长为 **15 天**」

这句话检索库里根本没有，是编的。「2.3 等待期」是**个人住院医疗**的章节号，
重疾E 的等待期写在 `2.3.1 身故保险金` 里——目录页反而把模型带偏了。

这正是 `docs/链路实测发现报告.md` 发现三预告过的问题：**目录里也写着章节名**。
**这是数据侧问题，不是参数问题**：要么把目录/封面页从知识库里剔掉，要么靠提示词禁止拿目录当依据。

### 5.2 拒答被「有引用」绑架（3 条）

模型答了「未找到相关信息」（正确行为），但 Dify 的 `refused` 标记只由「检索节点有无结果」决定，
阈值一降就有结果 → `refused=false` → 被判成误答。
这类「答对了但被系统判错」的情况一度让评测结论偏悲观，
已修正判据（拒答判定同时看 `refused` 标记、引用数量、**正文拒答话术**三个信号）。

## 6. r004：提示词改版是净负，已回滚

针对 §5 的两类问题（目录页导致模型用行业常识编答案、不同产品答案被混为一谈），
在原提示词上加了 3 条规则（`eval/prompts/system_v2.txt`）：动笔前先判断内容出自哪一份条款、
只在一份时须写明产品名；多份产品给出不同答案时必须分别列出；问题未指明产品时不要自行假定。
另加一条：金额/保额/时效若条款正文没写死，说明以保险单或附表载明为准，不要编数字。

结果：

| 指标 | r003（原提示词） | r004（提示词 v2） | Δ |
| --- | --- | --- | --- |
| 应答类 | **20/42** | 17/42 | −7pp |
| 引用命中 | 22/34 | 22/34 | 0 |
| 误拒率 | **5%** | 12% | +7pp |
| 无据之答 | 7% | **5%** | −2pp |
| 逐条 | — | **修好 0 条，改坏 3 条** | |

**修好 0 条、改坏 3 条**，已 `--restore` 回滚到原提示词。

改坏的 3 条很说明问题：

- **X-01「住院医疗险和重疾险的等待期分别是多久？」→ 变成拒答。**
  规则 4.2 要求「分别列出每个产品各自的答案」，但这条规则让模型在对比题上过度谨慎，
  反而不敢作答。**「把规则写细」不等于「模型能照做」**，措辞过强会反噬。
- **C-07「出险后想退保能退多少？」→ 变成拒答。**同类问题，被新规则劝退。
- **M-10「住院医疗险最高能赔多少钱？」→ coverage_gap。**期望的答案是指出「保额见保险计划表」，
  新规则让模型改说「以保险单载明为准」，意思对但没提「保险计划表」四个字。

同时它确实修好了幻觉：**O-07「一年交多少钱」不再编价格**（r003 编了，r004 正确拒答）、
**F-02「帮我查保单」不再用身份证号去检索**、M-07 / O-03 也都正确拒答。

> 判断：**这版提示词修掉的是「危险但低频」，代价是「正常但高频」**。
> 如果后续要保留，应该逐条拆开、只留「不得编数字」一条单独验，而不是整版一起上。
> 本轮按数据回滚，不硬撑。

## 7. 遗留问题与下一步

### 7.0 最终配置（当前线上生效）

| 位置 | 参数 | 原值 | 现值 |
| --- | --- | --- | --- |
| **已发布 workflow 检索节点** `multiple_retrieval_config.score_threshold` | 阈值 | 0.3 | **0.1** ← 真正生效的那一档 |
| 知识库 `datasets.retrieval_model.score_threshold` | 阈值 | 0.3 | 0.1（跟着改，避免以后误判） |
| 知识库 `top_k` | 候选数 | 30 | 30（未改，**不要调到 33 以上**） |
| 向量/关键词权重 | — | 0.7/0.3 | 0.7/0.3（实测无效，不值得调） |
| LLM `temperature` / `top_p` | — | 0.1 / 1.0 | 未改 |
| system 提示词 | — | v1 | v1（r004 试过 v2，净负已回滚） |

### 7.1 参数已到头，架构才是天花板

四轮迭代后剩下的失败集中在同一处：**三份条款放在同一个知识库、检索前没有任何产品约束**。
42 条应答题里 4 条串档、3 条同名章节错配（个人医疗「2.7 责任免除」vs 重疾E「2.4 责任免除」，
标题一样编号不同，最隐蔽），阈值和权重都无能为力。

按 `docs/链路实测发现报告.md` 的建议，下一步是**拆两个知识库 + 问题分类器路由**，
而不是继续调阈值。

### 7.2 知识库里混着目录页

52 条里有 30% 的查询，前 3 条引用中出现「阅读指引/条款目录/释义」页。
清理掉这部分片段，比再调一轮阈值收益大得多。

### 7.3 ⚠️ 前端 SSE 有真实缺陷（与本次调参无关，但更要紧）

`delta` 增量拼出来的文本和 `done.answer` **对不上**：r001 里 38/52 条不一致。

抓原始字节流确认了根因，不是评测脚本的问题：

```
event:delta⏎data:  **      ← Spring 写的，冒号后没有空格
```

SSE 规范要求客户端剥掉 `data:` 后的**一个**前导空格。前端
（`App.jsx:53`）和本评测器都照规范剥了，于是**每个以空格开头的增量都会丢掉那个空格**：

| delta 拼接（前端看到的） | done.answer（最终定稿） |
| --- | --- |
| `1. **一般医疗保险金**` | `1.  **一般医疗保险金**` |
| `之日起30日内` | `之日起 30 日内` |

中文里多数是观感问题，但**一旦某个增量块里有换行且换行后有实义内容，那部分会被静默吞掉**。
修法二选一：服务端保证 `data:` 后带一个空格（合规），或客户端改成不剥（对不合规服务端有效）。
