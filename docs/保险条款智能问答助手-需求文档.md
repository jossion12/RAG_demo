## 1. 项目概述

### 1.1 项目背景

保险条款文档动辄几十页、专业术语密集，客户与营销员都难以快速定位"等待期""免责条款""理赔条件"等关键信息。传统做法依赖人工翻阅，效率低且易遗漏。本项目通过检索增强生成（RAG）技术，将非结构化的保险合同/条款文档转化为可对话、可溯源的知识问答系统。

### 1.2 项目目标

- **功能目标**：用户通过自然语言提问，系统返回准确答案，并附答案来源出处。
- **质量目标**：答不准时宁可拒答也不编造，保证金融合规场景的信息可靠性。
- **技术目标**：以 Dify 承载 RAG 链路（切片 / 向量 / 混合检索 / Rerank / 生成），以 Java Spring Boot 承载**业务治理层**（会话编排、审计留痕、敏感过滤、引用组装、效果评测），验证"Java + AI"在真实业务治理场景的落地能力。

> **关于技术目标的诚实说明**
> 本方案选择 Dify 编排 RAG 链路，代价是：切片策略、相似度阈值、TopK 等参数**不在 Java 代码里，而在 Dify 的知识库/工作流配置中**，可被 Java 单测覆盖的范围显著缩小。
> 这是为"3 天出可演示系统"做的取舍，面试时应主动说明，而不是回避。
> **补偿手段**：Java 侧不作为透传壳，而是承担 Dify 不覆盖的六件事——会话编排、审计留痕、输入输出敏感过滤、引用结构化组装、文档生命周期管理、**批量效果评测**（见 FR-09）。§4.3 的全部合规需求都落在 Java 侧，这是本架构下 Java 的真实价值所在。

### 1.3 项目范围

**In Scope（本期实现）**

- 保险条款 PDF 的上传、解析入库（由 Dify 知识库承载）
- 基于 RAG 的语义问答（混合检索 + Rerank）
- 答案溯源与条款原文回看
- 检索质量不足时的兜底拒答
- Java 侧治理层：会话、审计、敏感过滤、引用组装
- **离线评测集与效果基线报告**
- 基础 Web 对话界面（SSE 流式）

**Out of Scope（本期不实现）**

- 生产级高可用集群与灾备
- 多租户与完整权限体系（Demo 不做登录鉴权，仅单演示用户）
- 精算 / 核保业务逻辑
- 移动端 App
- **多轮指代消解**（V1 明确为单轮，见 FR-05）

### 1.4 名词术语

| 术语 | 说明 |
| --- | --- |
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| Chunk / 切片 | Dify 将长文本切分为有语义边界的片段 |
| Embedding | 将文本转换为向量表示 |
| Rerank | 对召回结果重新打分排序，提升相关性 |
| Score 阈值 | 低于该相似度分数的片段不被召回，是兜底拒答的唯一依据 |
| TopK | 参与召回的片段数量上限 |
| BFF | Backend For Frontend，面向前端的聚合/治理层 |
| 兜底拒答 | 检索质量不足时拒绝作答，不编造 |

## 2. 用户与使用场景

### 2.1 目标用户

| 角色 | 特征 | 使用诉求 |
| --- | --- | --- |
| 客户 | 非专业用户 | 用自然语言快速查条款要点 |
| 保险营销员 | 一线业务人员 | 快速定位理赔、免责、等待期等关键条款 |
| 面试官（本项目额外受众） | 技术评审 | 评估 Java 治理层设计 + RAG 效果调优能力 |

### 2.2 核心使用场景

1. 用户上传保险条款 PDF，系统自动解析入库并可在文档列表中看到解析状态。
2. 用户提问"住院医疗险的等待期是多久？"，系统返回答案 + 引用来源。
3. 用户提问知识库中不存在的内容（如"这款产品的收益率是多少"），系统明确回复"未找到相关信息"，不编造。
4. 用户点击答案中的引用，可回看对应条款原文片段与所属产品。
5. **研发侧**：运行离线评测脚本，输出一组问题在当前参数下的命中率 / 拒答率，作为调参依据（FR-09）。

## 3. 功能需求

### 3.1 功能模块划分

```
保险条款智能问答助手
├── [Dify 承载]
│   ├── 知识库构建：文档上传 / 解析 / 切片 / 向量化入库
│   └── 检索生成：问题向量化 → 混合检索 → Rerank → 阈值判定 → LLM 生成
├── [Java 承载 · 治理层]
│   ├── 文档管理：上传编排、状态映射、删除
│   ├── 会话管理：多轮会话落库、历史查询
│   ├── 引用组装：Dify metadata → 结构化 Citation
│   ├── 安全合规：输入/输出敏感过滤、审计留痕
│   └── 效果评测：批量跑评测集，输出准确率/拒答率报告
└── 前端
    ├── 对话界面（SSE 流式 / 中断 / 重试）
    └── 文档管理 + 溯源回看
```

#### FR-02 文档解析与切片（由 Dify 执行）

| 编号 | FR-02 | 责任人 |
| --- | --- | --- |
| 描述 | 将 PDF 转为文本并按语义边界切片 | Dify + 预处理 |

| 约束 | ⚠️ **高质量索引方式一经创建不可切换为经济型**，选错无法回退 | |
| 优先级 | 高 | |

#### FR-03.5 产品路由（**V1.2 新增，实测驱动的架构变更**）

| 编号 | FR-03.5 | 责任人 |
| --- | --- | --- |
| 描述 | 提问先判定险种，再在**单一产品范围内**检索 | Dify Chatflow |
| **实测问题** | 问「重疾险的等待期是多久？」，实测返回的是**医疗险**的等待期条款，score **0.7152**；正确答案（重疾 2.3.1 身故保险金中「90 日为等待期，下同」）score 仅 0.1959 排第三 | |
| **危害** | 0.7152 **会通过 Score 阈值 0.5**，LLM 随后基于错误产品的条款生成一个看似合理的答案。客户问重疾却拿到医疗的等待期数字——不是拒答，是**自信地答错**，保险场景下最危险 | |
| **根因** | 医疗险有独立章节「2.3 等待期」，语义锚点强；重疾 E 款**没有独立的等待期条款**，等待期写死在 2.3.1 身故保险金内，「等待期」仅作括注出现，权重远低于独立章节 | |
| 处理 | ①两份条款拆成**两个独立知识库**；②Chatflow 开头加**问题分类器节点**，路由到「重疾 / 医疗 / 无关」；③「无关」类**直接走拒答分支，不进入检索**（比"检索完再判分数低"更省时也更可靠）；④分类结果同时作为**元数据过滤条件**兜底，防止分类器误判时跨库召回 | |
| 输出 | 路由结论 + 目标知识库 | |
| 验证 | 评测集须包含**跨产品对比题**（问重疾、答重疾），用于盯住这个回归 | |
| 优先级 | **高（不实现则 AC-02 与 AC-04 无法同时成立）** | |

| 编号 | FR-04 | 责任人 |
| --- | --- | --- |
| 描述 | 自然语言提问，返回带溯源的答案 | Java 调 Dify |
| 处理 | Java 调 Dify Chatflow API（SSE 流式），透传 token；结束后解析返回的 metadata，组装结构化引用 | |
| 输出 | 答案文本 + 引用列表 | |
| 优先级 | 高 | |

#### FR-05 兜底拒答与单轮约束

| 编号 | FR-05 | 责任人 |
| --- | --- | --- |
| 描述 | 检索质量不足时拒绝作答 | Dify |
| 处理 | **两级拒答**：①**路由级**——问题分类器判为「无关」时不进入检索，直接拒答（FR-03.5）；②**阈值级**——检索后 Score 阈值过滤，无片段过阈值则不进入 LLM 生成 | |
| 决策记录 | V1.0 中"是否额外调一次 LLM 判能否作答"悬而未决。**结论：不额外调用**。理由：Dify 架构下这会引入一次完整推理延迟，与 §4.1 的 3 秒预算冲突；且阈值拒答的误拒率可通过评测集（FR-09）量化后调阈值解决，无需 LLM 兜底 | |
| **阈值实测结论（V1.2）** | 库外题表现可靠（最高 0.0102）；但**跨产品误召回高达 0.7152**，导致「最低应答分 0.0151」与「最高无关分 0.7152」完全重叠，单一全局阈值无法同时保证不漏答与不误答。**结论：先做 FR-03.5 产品路由，再谈阈值数值**；路由到位后在各产品内单独调优 | |
| 输出 | 拒答提示语 | |
| 单轮约束 | **V1 明确为单轮问答**。前端会话历史仅作展示，不做指代消解；问题"它的等待期呢"将被拒答，属预期行为 | |
| 优先级 | 高 | |

#### FR-09 离线评测集（**核心交付物**）

| 编号 | FR-09 | 责任人 |
| --- | --- | --- |
| 描述 | 用固定评测集量化检索与生成质量，作为调参依据 | Java / 脚本 |
| 规模 | **30~50 条**，覆盖：重疾险 15 条、医疗险 15 条、跨产品对比 5 条、知识库外拒答 5 条 | |
| 每条字段 | `id`、`product`、`question`、`expected_answer_points[]`（关键信息点）、`expected_clause`（期望命中的条款/章节）、`expect_refuse`(bool) | |
| 执行 | 脚本批量调 `/api/chat`，逐条比对：① 答案是否覆盖全部 points（LLM 判分或关键词匹配）；② 引用是否命中期望条款；③ 该拒答的是否拒答 | |
| 输出 | `eval-report.md`：总命中率、分类命中率、拒答率、平均耗时、单条失败明细 | |

| **问法要求（V1.2，实测依据）** | **以口语问法为主，术语问法只占少数。** 实测同一份免赔额条款：「免赔额是多少？」得 0.7567，「住院医疗险要自己先垫多少钱？」仅 0.0156，**相差 48 倍**。若评测集全用术语问法，恰好只测 rerank 最擅长的形态，会给出虚高分数 | |
| **跨产品对比题（V1.2 新增）** | 至少 5 条「问 A 产品、答案必须来自 A 产品」的题，专门盯住 FR-03.5 的回归。实测中该类题是主要失败来源 | |
| **种子（已从真实条款原文提取，期望答案有出处）** | ① 医疗险 §2.3 等待期 = **30 日**（含第 30 日）<br>② 医疗险 §2.4 一般医疗免赔额 = **1 万元**；重疾医疗与质子重离子**无免赔额**<br>③ 重疾 §1.4 犹豫期 = **15 日**，期内退保扣工本费 **10 元**<br>④ 重疾等待期 = **90 日**，但它**写在 §2.3.1 身故保险金内**（「90 日为等待期，下同」），**不在独立章节**——这条专门检验 FR-03.5<br>⑤ 库外题：「这款保险的年化收益率是多少？」→ 必须拒答 | |
| 优先级 | **高（与 FR-01~FR-08 并列）** | |

### 3.3 核心业务流程（智能问答时序）

```
前端 → Java (BFF)
 1. 入参敏感过滤（身份证/手机号/银行卡掩码）
 2. 落库：question + sessionId，状态 = PENDING
 3. 调 Dify Chatflow API（SSE 流式）
      └─ Dify 内部：
         ① 问题分类器（FR-03.5）判定险种
              ├─ 无关 ──→ 直接拒答（不检索、不调 LLM）
              └─ 重疾 / 医疗
         ② 在对应知识库内：混合检索 → Rerank → Score 阈值过滤
              ├─ 无片段过阈值 → 拒答（不调 LLM）
              └─ 有片段过阈值 → LLM 生成 → 流式返回
         ③ 元数据过滤兜底，防止分类器误判导致跨库召回
 4. Java 边转发边累计；结束后解析 metadata → 结构化 Citation
 5. 出参敏感过滤
 6. 落库：answer + citations + scores + 耗时 + 是否拒答 + 路由结论
 7. 前端渲染答案 + 可点击引用 → 回看原文片段
```

> 拒答路径有**两级**：路由级（分类器判无关，零检索开销）与阈值级（检索后分数不足）。实测表明跨产品误召回分数可达 0.7152，会骗过 0.5 阈值，因此路由级拒答不可省。

## 11. 附录

### 附录 A：面试讲法要点（STAR）

- **S 背景**：保险条款几十页、专业词密集，人工查阅效率低易遗漏；金融场景更怕"答错"。
- **T 目标**：自然语言查条款、答案带出处、答不准拒答。
- **A 行动**：
  1. **先用真实条款实测链路，再定参数。** 没照着默认值走：实测发现「问重疾、返回医疗条款」的跨产品串档，错误答案得分 0.7152 会骗过 0.5 阈值——这类错误不是拒答，是**自信地答错**，金融场景最危险。由此新增产品路由（双知识库 + 问题分类器 + 元数据兜底）。
  2. 同样实测出「口语问法 vs 术语问法分数差 48 倍」，据此把评测集定为口语问法为主，避免用 rerank 最擅长的形态给自己虚高分数。
  3. 解析侧解决条款 PDF 的两类噪声：`-layout` 的多列对齐噪声与原始印刷行号；并区分目录条目与正文条款。
  4. 用 **Dify 编排 RAG 链路**（高质量索引 + 混合检索 + Rerank + 两级拒答），聚焦把检索质量调到位；
  5. 用 **Java Spring Boot 做治理层**：会话编排、敏感过滤、审计留痕、引用组装、文档生命周期、**批量评测**；
  6. **建立 30~50 条离线评测集**，让阈值/TopK/切片的每次调整都有量化依据。
- **R 结果**：常见条款问题答准且可溯源，库外问题明确拒答不编造；跨产品题与口语题单列验收项，防止回归；交付"调参前后准确率对比"的实证报告。
- **技术诚实点（主动讲，加分）**：检索参数配在 Dify 而非 Java 代码中，这是 3 天 Demo 的取舍；因此我把价值放在 Java 真正能发力的治理与评测层。另外我在实测中也修正过自己的一个错误结论——曾因抽取脚本只取关键词首次出现（落在目录页）而误判"重疾条款里没有'等待期'一词"，实际正文 2.3.1 写着「90 日为等待期，下同」。判据返回"未找到"时，先怀疑判据。

### 附录 B：关键追问预演

| 追问 | 参考回答 |
| --- | --- |
| **你怎么发现跨产品会答错的？** | 我在调参前先拿真实条款跑了一轮 rerank 打分。问"重疾险等待期"，返回的是**医疗险**的条款且得分 0.7152，而正确答案只有 0.1959。关键在于 0.7152 **能通过默认 0.5 阈值**——这不是拒答，是自信地答错，比拒答危险得多。根因是医疗险有独立「2.3 等待期」章节，而重疾的等待期写死在「2.3.1 身故保险金」里，「等待期」只是括注。解法是加问题分类器做产品路由 + 元数据过滤兜底 |
| **阈值定多少？** | 现在**不定**。实测正负样本完全重叠（最低应答 0.0151 vs 最高无关 0.7152），单一全局阈值不可能同时不漏答和不误答。正确顺序是先做产品路由，路由到位后正负分布在各产品内收窄，再用评测集扫描定值 |
| **口语问题会不会答不出来？** | 会，这是实测到的真问题。同一份免赔额条款，「免赔额是多少？」得 0.7567，「住院医疗险要自己先垫多少钱？」只有 0.0156，**差 48 倍**——口语表达和条款术语之间没有字面重叠。所以评测集我以口语问法为主，术语问法只占少数，否则等于只测 rerank 最擅长的形态 |
| **为什么不用 Ollama 做 Rerank？** | 试过，`/api/rerank`、`/v1/rerank` 都是 404——Ollama 根本没有 rerank 端点。Dify 的 Ollama 插件 manifest 里声明了 rerank 支持，但实际调用会失败。所以改用 TEI 跑 `bge-reranker-v2-m3`，`/info` 返回 `model_type: reranker`，正是 Dify 校验要的那个字段 |
| 切片重叠设多少？ | 10%~20%，在 Dify 知识库分段设置中配置；具体值靠评测集验证，不靠经验值 |
| 为什么不把两份条款放进同一个知识库？ | 最初想过，实测否掉了——多产品混在一个库里时，靠 rerank 分数区分产品不可靠（见上面第一题）。拆成两个库 + 先分类再检索，是更硬的一道约束 |
| 条款 PDF 解析上踩过什么坑？ | 两个：①`-layout` 提取会产生 260 行多列对齐噪声，会切碎语义单元污染 embedding，改用 `-raw`；②条款 PDF 排版带原始印刷行号，三种模式都残留 86~137 行，必须显式剔除。还有一个是目录里也写着「2.3 等待期」，按关键词取首个匹配会抓到目录行而不是正文 |
| Dify 里的 Score 阈值怎么定？ | 先确认一件事：**Score 阈值与 TopK 只在启用 Rerank 模型后生效**。不配 Rerank，这两项配置是无效的——这是踩过的坑 |
| 为什么用 Dify 编排而不是 Java 自研？ | 3 天周期内自研要处理切片、向量库、混合检索、Rerank 的全部工程细节；用 Dify 把时间留给两件更有区分度的事——Java 治理层与离线评测。代价我清楚：参数不在代码里，可测性下降，所以我补了评测集来补这块 |
| 为什么选 Weaviate 而不是 Qdrant？ | 环境里 Dify 默认就是 weaviate，且跑得健康。weaviate 同样支持过滤与混合检索，Demo 够用；真要换改 `VECTOR_STORE` 一个变量即可，我没有为了对齐文档去动一个正在运行的环境 |
| 怎么证明 RAG 是调好的而不是玄学？ | 30~50 条评测集，每次参数改动跑一遍出对比报告；评测集覆盖跨产品对比、口语问法、库外拒答三类，后两类专门用来抓"过度拒答"和"串产品" |
| 并发量大怎么扛？ | 本项目是单卡 Demo，实测 2~3 并发；生产方案是检索缓存、向量库水平扩展、模型多副本 |
| 多轮对话为什么不做？ | V1 明确单轮。指代消解需要改写查询后再检索，会引入额外延迟和失败模式，三天内做扎实单轮比做半成品多轮更有价值 |
