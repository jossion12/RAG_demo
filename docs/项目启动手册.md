### 2.1 Ollama —— 必须用 serve 模式直启

```powershell

$env:OLLAMA_KEEP_ALIVE="-1"
Start-Process "C:\Users\Administrator\AppData\Local\Programs\Ollama\ollama.exe" `
  -ArgumentList serve -WindowStyle Hidden
```

验证（两个模型都要在）：

```powershell
C:\Python312\python.exe -c "import json,urllib.request;print([m['name'] for m in json.loads(urllib.request.urlopen('http://127.0.0.1:11434/api/ps').read())['models']])"
# 期望：['bge-m3:latest', 'qwen3.5:9b']
```

**为什么不能用托盘程序启动：** 从 `ollama app.exe` 启动时，`OLLAMA_MAX_LOADED_MODELS` / `OLLAMA_KEEP_ALIVE` 传不进 serve 进程（实测设了也无效，bge-m3 仍不驻留），延迟尖峰照旧。直启 serve 则实测有效：两模型同时驻留，重复调用 0.2s。

**重启 Ollama 后必须清理孤儿进程**（见 §6.1）：

```powershell
$serve = (Get-CimInstance Win32_Process -Filter "Name='ollama.exe'").ProcessId
$keep  = (Get-CimInstance Win32_Process -Filter "Name='llama-server.exe'" |
          Where-Object { $_.ParentProcessId -eq $serve }).ProcessId
Get-CimInstance Win32_Process -Filter "Name='llama-server.exe'" |
  Where-Object { $keep -notcontains $_.ProcessId } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

### 2.4 Java 后端

构建（jar 已存在时可跳过）：

```powershell
cd D:\project\private\new_life\local\RAG_demo\backend
$env:JAVA_HOME="C:\Program Files\Eclipse Adoptium\jdk-17.0.20.101-hotspot"
D:\tool\maven\apache-maven-3.9.9\bin\mvn.cmd -q -DskipTests package
```

启动：

```powershell
cd D:\project\private\new_life\local\RAG_demo
powershell -ExecutionPolicy Bypass -File scripts\start-backend.ps1
```

脚本会：
1. 从 `api_tokens` 表读 Dify 应用 API Key 注入 `DIFY_APP_API_KEY`（**只打印前缀 `app-xxxxx***`，明文不落盘**）
2. **端口预检**：8080 已被占用时直接报出占用进程的 PID + 命令行并退出（退出码 **2**），不会替用户杀进程；确实要换新实例就加 `-ForceRestart`，它会先停旧实例、等端口真正释放再起
3. 以 `-Dapp.data.dir=<绝对路径>` 启动 jar，把 PID 写进 `backend/backend.pid`
4. 就绪判据是「**刚起的这个 PID 自己监听了 8080**」，不是「8080 上有人」——旧实例还活着时，端口判据会被旧实例喂饱，脚本就会在新实例已经崩掉的情况下误报 OK

退出码：`0` 成功 / `1` 启动失败 / `2` 端口被占用。失败时会打印日志尾部；若本次启动一行日志都没写，说明进程死在 Spring 日志初始化之前（JVM 级失败），脚本会明确提示**那份日志是上一次启动的**，别照着它排查。

重启：**不用再抄 PID**，直接跑 `scripts\stop-backend.ps1`。

```powershell
cd D:\project\private\new_life\local\RAG_demo
powershell -ExecutionPolicy Bypass -File scripts\start-backend.ps1 -ForceRestart
```

注意：**必须用 `powershell` 而非 `pwsh`**，脚本文件需保持 UTF-8 BOM。

**打包前必须先停后端**：jar 正被运行中的 java 进程加载时，`mvn package` 会在 `spring-boot:repackage` 阶段报
`Unable to rename '...jar' to '...jar.original'`（Windows 文件锁），并且**已经用 37KB 的瘦 jar 覆盖掉了原来的 fat jar**——产物不可执行。先 `stop-backend.ps1` 再打包。

## 4. 当前关键配置速查

改配置请用修复脚本，别在 Dify UI 里改（原因见 §6.4）：

```powershell
C:\Python312\python.exe -X utf8 scripts\fix_workflow_all.py            # 预览
C:\Python312\python.exe -X utf8 scripts\fix_workflow_all.py --apply    # 写库
```

| 配置 | 值 | 位置 |
| --- | --- | --- |
| `score_threshold` | **0.1** | 检索节点 `multiple_retrieval_config`（**运行时真正吃的那一档**）；知识库级同步为 0.1 |
| `top_k` | **30** | 同上。⚠️ **不要调到 33 及以上**，见下方说明 |
| `search_method` | `hybrid_search`（向量 0.7 / 关键词 0.3） | 知识库级 `datasets.retrieval_model` |
| `reranking_enable` | `true`，`bge-reranker-v2-m3` | 同上 |
| `retriever_resource.enabled` | **true** | `workflows.features`（**不是** app_model_configs） |
| `completion_params.think` | **false** | 工作流 LLM 节点 `model.completion_params` |
| `completion_params.temperature` | 0.1 | 同上 |
| 知识库 ID | `b840bb7a-6289-4b5e-a09a-55e61e74043c` | — |
| 应用 ID | `f5939e3a-5fd7-43e7-8824-54d6ed1bc8da` | — |

**「为什么阈值从 0.3 降到 0.1」**：2026-10-12 跑了四轮端到端评测（详见 `docs/评测迭代报告.md`）。
阈值 0.3 时**误拒率 26%**（42 条应答题里 11 条被拒），降到 0.1 后降到 **5%**，
引用命中率同步从 50% 升到 65%。代价是上下文变长（平均引用 2.9 → 6.5 条），
需要配合清理知识库里的目录页——详见报告 §5。

**⚠️ `top_k ≥ 33` 会静默返回空集**：实测 30/31/32 正常，33 及以上 **HTTP 200、0 条记录、零异常**。
在 Dify 界面把 top_k 设成 33 以上，问答不报错、不告警、什么都答不出来。排查「突然全答不出」时先看这一项。

**「为什么 top_k 是 30 而不是 8」**：`hybrid_search` 只取 top_k 条候选进 rerank 池。实测 top_k=8 和 15 时，语料里「自本合同生效之日起 30 日内（含 30 日）为等待期」那段根本进不了池，LLM 只能答「未找到相关信息」；top_k=30 时它以 0.7381 分排到第 1，答案正确。实测 30 之后进入平台期，再大无收益（且 33 以上直接失效）。

**向量/关键词权重不用再调**：2026-10-12 扫过 0.1 / 0.5 / 0.7 / 0.9 四档，
章节命中率**全部相同**（79%），rerank 开着关掉都一样——这个旋钮在当前工作点对候选集没有影响。

## 6. 常见故障

### 6.1 延迟偶发 7~9s，且显存爆满

**症状**：单次问答时快时慢；`nvidia-smi` 显示 21765/22528 MiB。

**根因**：重启 Ollama 后，上一代的 `llama-server.exe` 子进程**不会随之退出**，成为孤儿继续占显存。实测连续三代 serve 留下 4 个孤儿，白占 12.3GB。显存打满后 Ollama 在两模型间反复换入换出。

**排查**：

```powershell
Get-CimInstance Win32_Process -Filter "Name='llama-server.exe'" |
  Select-Object ProcessId,ParentProcessId
# 进程数 > 已加载模型数（2）= 有孤儿
```

**处理**：执行 §2.1 的清理命令。验收：`nvidia-smi` 回落到 ~9464 MiB，且进程数 = 2。
实测清理前 Embedding max 7.374s → 清理后 **0.103s**。

### 6.2 答案里混进 `<think>` 思维链

**症状**：答案开头是 `<think>...</think>`，首 token 十几秒。

**根因**：Ollama 插件 `models/llm/llm.py:412` 的 `_wrap_thinking_by_reasoning_content` **故意**把 `message.thinking` 用 `<think>` 标签拼进正文。

**处理**：在工作流 LLM 节点的 `model.completion_params` 里设 `"think": false`（插件 llm.py:210 会 pop 到 Ollama 顶层 `data["think"]`）。实测 197 tokens/3.2s → 2 tokens/0.1s。

### 6.3 引用（`retriever_resources`）恒为空

**症状**：答案正常，但 `citations: 0`。

**根因**：`core/app/apps/advanced_chat/app_config_manager.py:27` 里 `additional_features` 来自 **`workflow.features_dict`**，不是 `app_model_configs`。开关关着时 `message_cycle_manager.handle_retriever_resources` **静默跳过**（不报错、不抛异常）。另外若 `apps.app_model_config_id` 为 NULL（`app_model_configs` 整表空），`additional_features` 为 None，handler 第一行直接 `raise ValueError("Additional features not found")`。

**处理**：跑 `scripts/fix_workflow_all.py --apply`，它同时修 workflow features 和补 AppModelConfig 行。验证用 `scripts/quick_probe.py`。

### 6.4 工作流修改被覆盖 / 设置改了不生效

**症状**：命令行改完库，刷新页面又变回去。

**根因**：Dify 工作流画布把整份图存在前端状态里，**保存时全量覆盖**。已连续发生三次。

**处理**：

- 改配置一律走 `scripts/fix_workflow_all.py`，不要用画布。
- 如果确实要用画布，**先完全关掉旧标签页**（不是刷新），再开新的。
- 改完用 `scripts/export_all_graphs.py` 复验（13 项断言）。

### 6.5 改了知识库级阈值没反应 🔴

**症状**：把 `datasets.retrieval_model.score_threshold` 从 0.3 改成 0.1，检索结果条数不变。

**根因**：**运行时吃的是已发布 workflow 里检索节点的 `multiple_retrieval_config.score_threshold`**，
知识库级那一档根本不参与。2026-10-12 用全量 52 条评测量化过：

| 只改知识库级 0.3 → 0.1 后 | r001 基线 | 实测 |
| --- | --- | --- |
| 平均引用条数 | 2.87 | **2.87**（0 条变化） |
| 首条分数均值 | 0.7302 | **0.7302**（0 条变化） |

改的是 `apps.workflow_id` 指向的那份 `workflows.graph`（**已发布版**，不是 draft）。

**处理**：调阈值要**两处一起改**。本项目用 `scripts/dify_params.py`：

```powershell
# node. 前缀 = 检索节点级（真正生效的那一档）；不带前缀 = 知识库级
python scripts\dify_params.py --set node.score_threshold=0.1 score_threshold=0.1
python scripts\dify_params.py --show        # 回读确认
```

⚠️ **同名坑**：`score_threshold` 在两层都叫这个名字。脚本里若按
`if key in dataset: ... continue` 的顺序匹配，会永远只改到知识库级、永远碰不到节点级，
表现出来就是「改了没反应」。`dify_params.py` 已用 `node.` 前缀显式区分。

> 另见 `docs/Dify-RAG工作流搭建手册.md` §9.2——那里从源码角度说明了
> 「节点级检索参数整体替换知识库级，不是叠加」，两处结论一致。

### 6.6 宿主机访问 80 端口不通

**症状**：`http://localhost/v1/chat-messages` TCP 能连上但立即被关闭。

**处理**：`docker restart docker-nginx-1`。

### 6.7 导出/校验脚本报编码错误

PowerShell 的 `>` / `Out-File` 会用控制台编码（中文 Windows 通常 GBK）重编码原生命令的 UTF-8 输出，中文被截断。脚本内部已改走 subprocess 字节通道。手工导出时用：

```powershell
C:\Python312\python.exe -X utf8 脚本.py | Out-File -Encoding utf8 out.txt
```

### 6.8 后端日志中文乱码（已修）

**症状**：`backend.log` 里中文全是 `?`，或用 UTF-8 工具打开变乱码。

**根因**：JVM 没显式指定日志字符集时用**平台默认**（中文 Windows = GBK），而日志文件按 GBK 写、`Get-Content` 按 UTF-8 读，必然对不上。

**已修**：`application.yml` 增加

```yaml
logging:
  charset:
    file: UTF-8
    console: UTF-8
```

改完**必须重新打包**才生效（该配置打进 jar）。

**注意存量日志是混合编码**：改配置之前写的行仍是 GBK，之后写的是 UTF-8，同一个 `backend.log` 里两种都有。整份按单一编码解码一定会失败——`start-backend.ps1` 里的 `Get-LogTail` 因此**逐行**解码（先试严格 UTF-8，失败退 GB18030），老行新行都能正常读。日志按天轮转（`backend.log.YYYY-MM-DD.0.gz`），几天后自然全是 UTF-8。
